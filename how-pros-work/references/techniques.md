## 기본 전제

제안의 근거가 되는 원리입니다. 사용자에게 이유를 설명해야 할 때 이 내용을 활용하십시오.

- 모델의 주의력은 유한한 예산과 같습니다. 컨텍스트에 토큰이 늘어날수록 그 안의 정보를 정확하게 회수하는 능력은 떨어집니다. 이 현상은 정도의 차이가 있을 뿐 모든 모델에서 나타납니다.
- 트랜스포머 구조에서는 토큰 n개가 서로 n²개의 관계를 맺기 때문에, 컨텍스트가 길어질수록 관계를 포착하는 능력이 얇게 퍼집니다. 급격히 무너지는 절벽이 아니라 완만한 성능 기울기에 가깝습니다.
- 따라서 좋은 컨텍스트 설계란, 원하는 결과를 얻을 확률을 최대화하는 **가장 작은 고신호 토큰 집합**을 찾는 일입니다. 작다는 것이 짧다는 뜻은 아닙니다. 필요한 정보는 충분히 주되 불필요한 것을 덜어낸다는 의미입니다.
- 코딩 에이전트에서 통용되는 요령의 대부분은 이 한 가지 제약에서 파생됩니다. 컨텍스트는 빠르게 차고, 차오를수록 성능이 떨어집니다.

## 컨텍스트 관리 기법

### 압축 (Compaction)

컨텍스트 한계에 가까워진 대화를 요약해서 새 컨텍스트로 다시 시작하는 방법입니다. 장기 작업에서 가장 먼저 꺼내는 수단입니다.

- 무엇을 남기고 무엇을 버릴지 고르는 것이 핵심입니다. 지나치게 공격적으로 압축하면, 나중에야 중요성이 드러나는 미묘한 맥락을 잃습니다.
- 남길 것: 확정된 결정, 미해결 문제, 구현 세부 사항. 버릴 것: 중복된 도구 출력, 이미 처리된 중간 메시지.
- Claude Code에서는 `/compact`에 지시를 덧붙일 수 있습니다. 예: `/compact API 변경 사항 위주로 정리해줘`
- 압축 시 반드시 보존할 항목을 CLAUDE.md에 미리 적어 둘 수도 있습니다. 예: "압축할 때 수정한 파일 목록과 테스트 명령은 항상 보존할 것"

### 구조화된 메모 남기기 (Structured note-taking)

컨텍스트 바깥의 파일에 진행 상황을 적어 두고, 필요할 때 다시 불러오는 방법입니다. NOTES.md나 할 일 목록이 전형적인 형태입니다.

- 컨텍스트가 초기화되어도 작업의 연속성이 유지됩니다.
- 명확한 이정표가 있는 반복 개발에 특히 잘 맞습니다.

### 필요한 시점에 불러오기 (Just-in-time retrieval)

모든 자료를 미리 올려 두는 대신, 파일 경로나 링크 같은 가벼운 식별자만 들고 있다가 필요할 때 도구로 불러오는 방법입니다.

- 색인이 낡을 걱정이 없고, 탐색 과정에서 얻은 파일 이름과 폴더 구조 자체가 판단의 단서가 됩니다.
- 대신 실행 시점 탐색은 미리 계산된 자료를 꺼내는 것보다 느립니다. 변동이 적은 자료라면 일부를 미리 올려 두는 혼합 방식이 낫습니다.

### 무관한 작업 사이에 초기화

성격이 다른 작업으로 넘어갈 때는 컨텍스트를 비우는 편이 낫습니다. Claude Code에서는 `/clear`입니다.

- 같은 문제로 두 번 이상 교정했다면, 컨텍스트가 실패한 접근으로 오염된 상태입니다. 이어서 교정하기보다 초기화한 뒤, 그동안 알아낸 것을 담아 더 구체적인 요청으로 다시 시작하는 편이 거의 항상 낫습니다.
- 컨텍스트에 남길 필요가 없는 곁가지 질문은 `/btw`로 물으면 대화 기록에 들어가지 않습니다.

### 되감기 (Checkpoint / rewind)

Claude Code에서는 매 요청마다 복원 지점이 생깁니다. `Esc`를 두 번 누르거나 `/rewind`로 대화만, 코드만, 또는 둘 다 되돌릴 수 있습니다.

- 신중하게 계획하는 대신 과감하게 시도하고 실패하면 되감는 전략이 가능해집니다.
- 단, 파일 편집 도구를 거친 변경만 추적되므로 bash로 만든 변경은 복원되지 않습니다.

## 토큰 절감 기법

컨텍스트 관리가 "무엇을 남길 것인가"를 다룬다면, 이 절은 "같은 결과를 더 적은 토큰으로 얻는 방법"을 다룹니다. 대화가 꼬이지 않았더라도 적용할 수 있습니다.

제안할 때는 반드시 세션에서 실제로 토큰을 많이 쓴 호출을 지목하십시오. 지목할 대상이 없으면 이 절의 기법을 꺼내지 마십시오.

### 읽는 범위 좁히기

파일 전체를 읽는 대신, 검색으로 위치를 먼저 찾고 필요한 구간만 읽습니다.

- 나쁨: 2000줄짜리 파일을 통째로 읽고 함수 하나를 고침
- 좋음: `grep -n "def evaluate_entry" src/foo.py`로 줄 번호를 찾은 뒤 `sed -n '60,90p' src/foo.py`로 해당 구간만 읽음
- 같은 파일을 통째로 두 번 읽었다면 두 번째 읽기는 대부분 낭비입니다. 이미 컨텍스트에 있기 때문입니다.

### 도구 출력 잘라내기

명령의 출력은 그대로 컨텍스트에 실립니다. Claude Code는 성공한 Bash 명령의 출력을 기본값으로 30000자까지 싣고(`bashOutputMaxChars`), 백그라운드 작업의 출력은 32000자까지 싣습니다(`taskOutputMaxChars`). 영어 산문 기준으로 1토큰이 대략 4자이므로, 상한에 가까운 출력 하나가 7000토큰을 넘습니다.

- 꼬리만 필요한 명령에는 `| tail -20`을, 목록에는 `| head -50`을 붙입니다.
- 테스트는 `pytest -q 2>&1 | tail -5`처럼 결과 줄만 받습니다.
- 변경 내용을 볼 때는 `git diff` 대신 `git diff --stat`으로 규모부터 확인합니다.
- 상한 자체를 낮추려면 settings.json의 `bashOutputMaxChars`를 조정합니다.

### 중간 산출물은 파일로 보내기

분석 결과나 대용량 데이터는 컨텍스트에 싣지 말고 파일에 저장한 뒤, 필요한 값만 출력합니다.

- 나쁨: 표 전체를 출력해서 눈으로 훑기
- 좋음: 결과를 CSV로 저장하고 요약 통계 몇 줄만 출력한 뒤, 나중에 필요해지면 그때 해당 행만 읽기
- 「필요한 시점에 불러오기」와 같은 원리를 도구 출력에 적용한 것입니다.

### 조사는 서브에이전트에 맡기기

「서브에이전트로 조사 분리하기」와 같은 기법입니다. 토큰 관점에서 다시 말하면, 조사 과정에서 읽은 파일 수십 개가 주 대화에 남지 않고 요약 몇 줄만 돌아옵니다. 탐색 범위가 넓을수록 절감 폭이 큽니다.

### 캐시를 깨지 않는 순서로 작업하기

대화의 앞부분이 그대로 유지되는 동안에는 앞서 처리한 내용이 캐시에서 재사용됩니다. 대화 앞부분을 되감아 수정하면 그 뒤의 내용이 다시 계산됩니다.

- 되감기는 유용한 수단이지만 공짜가 아닙니다. 방금 한 시도를 무를 때 쓰고, 세션 초반으로 자주 돌아가지 마십시오.
- 곁가지 질문은 `/btw`로 물으면 대화 기록에 들어가지 않습니다.

### 작업 성격에 맞게 모델과 노력 수준 낮추기

정형적인 작업에 가장 무거운 추론을 쓸 이유가 없습니다. 파일 이동, 포맷 정리, 단순 검색, 기계적인 치환이 여기에 해당합니다.

- Claude Code에서는 `/model`로 모델을, `/effort`로 추론 수준을 바꿉니다.
- 지금까지 쓴 비용은 `/cost`로 확인할 수 있습니다. 제안하기 전에 실제 수치를 확인하면 어림값이 더 정확해집니다.

## 요청 작성 기법

### 범위를 좁혀서 지정하기

어느 파일의, 어떤 상황을, 어떤 방식으로 다룰지 명시합니다.

- 나쁨: "foo.py에 테스트 추가해줘"
- 좋음: "foo.py에 대해 사용자가 로그아웃된 경우의 경계 상황을 다루는 테스트를 작성해줘. 목(mock)은 쓰지 말고."

### 근거가 될 자료를 지목하기

답을 추측하게 하는 대신, 답이 들어 있는 곳을 가리킵니다.

- 나쁨: "이 API는 왜 이렇게 이상하게 생겼어?"
- 좋음: "이 클래스의 git 이력을 훑어서 현재 API가 어떤 경위로 만들어졌는지 정리해줘."

### 기존 패턴을 참조시키기

코드베이스 안에 이미 있는 좋은 사례를 지목하면, 결과물이 기존 관례와 어긋나지 않습니다.

### 증상과 위치와 완료 조건을 함께 주기

- 나쁨: "로그인 버그 고쳐줘"
- 좋음: "세션 만료 후 로그인이 실패한다는 제보가 있어. src/auth/의 토큰 갱신 부분을 보고, 먼저 이 문제를 재현하는 실패 테스트를 쓴 다음 고쳐줘."

### 모델이 먼저 인터뷰하게 만들기

규모가 큰 작업에서는, 요구 사항을 다 적어서 주는 대신 모델이 질문하게 만드는 편이 낫습니다. 스스로 생각하지 못한 경계 상황과 절충점이 드러납니다.

- 예시 문구: "이런 기능을 만들려고 해. 질문 도구를 써서 나를 자세히 인터뷰해줘. 기술 구현, 사용자 경험, 경계 상황, 절충점을 물어보되 뻔한 질문은 빼고 내가 미처 생각 못 한 어려운 부분을 파고들어줘. 다 다루고 나면 명세를 SPEC.md로 써줘."
- 명세가 완성되면 **새 세션에서** 실행하십시오. 인터뷰 과정이 컨텍스트에 남아 있지 않은 상태로 구현에만 집중할 수 있습니다.

### 탐색 먼저, 계획 다음, 구현 마지막

접근 방식이 불확실하거나 여러 파일을 건드리는 작업이라면, 읽기만 하는 단계를 분리하는 편이 낫습니다. Claude Code의 계획 모드가 이 용도입니다.

- 다만 한 문장으로 변경 내용을 설명할 수 있는 작업이라면 계획 단계는 불필요한 부담입니다.

## 검증 기법

### 모델이 스스로 돌릴 수 있는 검사를 주기

가장 효과가 큰 단일 기법입니다. 검사 수단이 없으면 "다 된 것 같다"가 유일한 종료 신호가 되고, 사용자가 검증 루프 역할을 떠맡게 됩니다.

- 검사의 형태: 테스트 묶음, 빌드 종료 코드, 린터, 기준 파일과 출력을 비교하는 스크립트, 화면 캡처 비교.
- 요청 안에 검사 실행까지 포함시키십시오. 예: "구현한 다음 테스트를 돌리고, 실패하면 고쳐줘."
- 성공했다고 주장하는 대신 증거를 보여 달라고 요구하십시오. 실행한 명령과 그 출력을 확인하는 편이, 직접 다시 돌려 보는 것보다 빠릅니다.

### 단계별로 강도를 올리기

1. 요청문 안에서 검사를 지시하기 (어느 환경에서나 지금 당장 가능)
2. 세션 전체의 종료 조건으로 걸기 (Claude Code의 `/goal`)
3. 결정적 관문으로 만들기 (Stop 훅으로 검사를 스크립트로 걸어 통과 전에는 턴이 끝나지 않게 함)

### 다른 맥락에서 검토시키기

작업한 주체가 자기 결과를 채점하면 편향이 생깁니다. 별도 컨텍스트에서 변경 사항만 보고 검토하게 하면 결과를 독립적으로 판단합니다.

- 주의: 결함을 찾으라고 지시받은 검토자는 결함이 없어도 무언가를 보고합니다. 모든 지적을 좇으면 과잉 설계로 이어집니다. "정확성이나 명시된 요구 사항에 영향을 주는 것만 보고하고, 취향 문제는 빼라"고 범위를 한정하십시오.

## 자산화 기법

### 어디에 넣을지 판단하는 기준

| 대상 | 넣을 것 | 넣지 말 것 |
|---|---|---|
| 항상 적용되는 프로젝트 지침 (CLAUDE.md / AGENTS.md) | 추측할 수 없는 명령어, 기본값과 다른 규칙, 테스트 실행 방법, 저장소 관례, 환경 특이 사항 | 코드를 읽으면 알 수 있는 것, 표준 관례, 자주 바뀌는 정보, 상세 API 문서 |
| 스킬 | 가끔만 필요한 도메인 지식, 반복되는 작업 절차 | 매번 필요한 내용 |
| 메모리·선호도 설정 | 매 대화에서 되풀이하게 되는 배경과 형식 요구 | 한 번만 쓰이는 맥락 |

- 지침 문서는 짧게 유지하십시오. 각 줄에 대해 "이 줄을 지우면 실수가 생기는가"를 물어서, 아니라면 삭제합니다. 문서가 길어지면 정작 중요한 규칙이 묻혀서 무시됩니다.
- 규칙을 넣어 두었는데도 계속 지켜지지 않는다면, 문서가 너무 길어서 그 규칙이 파묻혔을 가능성이 큽니다.
- 반드시 예외 없이 실행되어야 하는 동작은 지침이 아니라 훅으로 만드십시오. 지침은 권고이지만 훅은 결정적입니다.

### 승인 피로 줄이기

사소한 승인을 반복해서 누르고 있다면, 검토가 아니라 클릭이 되어 버린 상태입니다.

- 안전하다고 판단되는 명령을 미리 허용 목록에 넣습니다.
- 샌드박스를 켜서 정해진 경계 안에서는 자유롭게 움직이게 합니다.

## 작업 분할과 병렬화 기법

### 서브에이전트로 조사 분리하기

조사 과정에서 읽은 파일은 모두 주 컨텍스트를 차지합니다. 별도 컨텍스트에서 조사하고 요약만 돌려받으면, 주 대화는 구현에 집중한 상태로 유지됩니다.

- 예시 문구: "서브에이전트를 써서 인증 시스템이 토큰 갱신을 어떻게 처리하는지, 재사용할 만한 기존 유틸리티가 있는지 조사해줘."

### 병렬 세션

- 작성자와 검토자를 다른 세션으로 나누면, 검토자가 자기가 쓴 코드에 편향되지 않습니다.
- 대규모 변경은 파일 목록을 먼저 만들게 한 뒤 나누어 처리합니다. 전체에 적용하기 전에 두세 개로 먼저 시험하고 요청문을 다듬으십시오.

## 알려진 실패 패턴

진단에서 이 패턴이 관찰되면 곧바로 지목하십시오. 이름이 붙어 있는 편이 사용자가 인식하기 쉽습니다.

| 패턴 | 증상 | 대응 |
|---|---|---|
| 잡탕 세션 | 한 작업을 하다가 무관한 질문을 끼워 넣고 다시 돌아옴. 컨텍스트가 관계없는 정보로 참 | 무관한 작업 사이에 컨텍스트를 비움 |
| 교정의 반복 | 고쳐 달라고 했는데 또 틀리고, 다시 고쳐 달라고 함 | 두 번 실패하면 초기화하고, 알아낸 것을 담아 더 나은 요청으로 다시 시작 |
| 과적재된 지침 문서 | 지침이 길어서 절반이 무시됨 | 가차 없이 덜어내고, 반드시 지켜야 할 것은 훅으로 전환 |
| 믿고 넘어가기 | 그럴듯해 보이는 결과물이 경계 상황을 처리하지 못함 | 검증 수단을 반드시 제공. 검증할 수 없으면 내보내지 않음 |
| 끝없는 탐색 | 범위를 정하지 않고 "조사해 줘"라고 해서 수백 개 파일을 읽음 | 탐색 범위를 좁히거나 서브에이전트에 위임 |

## 이 카탈로그를 쓸 때의 주의

- 여기 적힌 것은 출발점이지 규칙이 아닙니다. 하나의 복잡한 문제를 깊이 파고드는 중이라면 컨텍스트를 쌓아 두는 편이 나을 때도 있고, 탐색적인 작업이라면 계획 단계를 건너뛰는 편이 나을 때도 있습니다. 세션에서 관찰한 상황에 비추어 판단하십시오.
- 도구의 기능과 명령어는 계속 바뀝니다. 특정 명령이나 설정을 제안할 때는 `sources.md`에 적힌 공식 문서로 현재도 유효한지 확인한 뒤 제시하십시오. 조회 범위와 예산은 SKILL.md의 2단계를 따릅니다. 확인할 수 없다면 명령어 자체보다 기법의 이름과 의도를 중심으로 제안하십시오.
